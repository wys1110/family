# 개인·가족 할 일 분리 설계

## 결정

`family_todos`에 `visibility` 열을 추가한다. 기존 행은 기본값 `family`로 유지하고, 새 행은 `family` 또는 `private` 중 하나다. `private` 행은 `created_by = auth.uid()`인 작성자만 조회·수정·삭제할 수 있다.

## 접근 비교

1. 화면에서만 개인 항목을 숨기는 방식은 API로 다른 가족 계정이 읽을 수 있어 제외한다.
2. 개인 할 일 전용 테이블은 보안은 가능하지만 반복·완료·검색·백업 경로를 이중으로 만들어 제외한다.
3. 기존 테이블의 단일 범위 열과 RLS 정책 교체는 현재 저장·반복 로직을 유지하면서 DB 접근을 차단하므로 채택한다.

## 사용자 경험

- 할 일 화면에 `가족 할 일`과 `내 할 일` 전환을 둔다.
- 현재 범위가 빠른 추가와 새 할 일 대화상자의 기본값이 된다. 대화상자에서도 범위를 명시적으로 바꿀 수 있다.
- 개인 항목 화면은 `나만 확인해요`라고 표시한다.
- 캘린더 배지, 가족 인수인계, 공유용 알림은 `family` 항목만 사용한다.
- 검색은 현재 사용자에게 RLS로 허용된 개인 항목만 보여줄 수 있고, 다른 가족에게는 개인 항목이 응답되지 않는다.

## 보안·데이터 규칙

- 모든 기존 할 일은 `family`로 유지한다.
- INSERT는 현재 가족 구성원이며 `created_by = auth.uid()`일 때만 허용한다.
- SELECT/UPDATE/DELETE는 가족 항목이거나 작성자 본인의 개인 항목일 때만 허용한다.
- `created_by` 변경은 DB 트리거로 금지해 다른 구성원이 가족 항목을 개인 항목으로 탈취할 수 없게 한다.
- 클라이언트 요청은 항상 현재 `household_id`를 필터링한다. RLS는 최종 보안 경계다.
- 로그인하지 않은 기기 저장소는 단일 사용자만 접근하므로 `내 할 일`로 표시하며 가족 공개를 가장하지 않는다.

## 검증

- 마이그레이션 테스트는 범위 열, 기본값, 소유권 변경 방지, SELECT/UPDATE/DELETE 정책을 확인한다.
- UI 테스트는 범위 전환, 원격 매핑, 가족 전용 캘린더·인수인계 스냅샷을 확인한다.
- 실제 DB에는 마이그레이션 적용 후 RLS 정책과 기존 행 범위를 SQL로 확인한다.
