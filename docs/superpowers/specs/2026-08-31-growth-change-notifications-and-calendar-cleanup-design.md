# 성장 기록 변경 알림 및 일정 화면 정리 설계

## 목표

성장일기의 성장·수유·이유식·수면·기저귀·건강·병원·첫 순간 기록을 추가·수정·삭제할 때 기록자를 제외한 같은 가족 구성원에게 기존 웹 푸시와 알림함 알림을 보낸다. 일정 화면에서는 사용하지 않는 `패밀리 핸드오프`와 `오늘 한눈에 보기`를 완전히 제거한다.

## 범위와 완료 기준

- 성장 기록의 추가·수정·삭제가 알림 발송 대상이다.
- 알림 수신자는 같은 `household_id`의 다른 구성원이며 기록자는 제외한다.
- 알림에는 기록 종류, 기록 제목, 날짜와 핵심 값만 포함하고 메모·사진·개인 식별 정보는 포함하지 않는다.
- 수유는 수유 종류·양·시간, 기저귀는 종류, 성장은 키·몸무게·머리둘레를 알림 본문에 표시한다.
- 알림 클릭 시 성장일기 화면과 해당 기록 날짜를 연다.
- 기존 일정 변경 알림, 아침 브리핑, 알림함 읽음·삭제 기능은 유지한다.
- 일정 탭에서 `패밀리 핸드오프`와 `오늘 한눈에 보기`가 렌더링되지 않는다.
- 가족 검색에 사용하는 `family-utility.js`의 검색 기능은 유지한다.

## 추천 아키텍처

현재 일정 변경 알림이 사용하는 클라이언트 변경 감지 모듈과 `daily-briefing-push` Edge Function을 확장한다. 새 푸시 인프라나 데이터베이스 트리거는 추가하지 않는다.

1. `event-change-push.js`가 `events`와 `growth_entries`의 성공한 insert·upsert·update·delete 결과를 감지한다.
2. 성장 기록 변경은 `growth-change` 액션으로 현재 로그인 사용자와 가족 공간을 함께 Edge Function에 전달한다.
3. Edge Function은 요청 사용자를 검증하고, 같은 가족의 다른 구성원별로 `notifications` 행을 upsert한 뒤 활성 `push_subscriptions`에 푸시한다.
4. `notifications.source_type`에는 `growth`, `notifications.kind`에는 `growth_change`를 추가한다. 기존 RLS의 사용자 본인 조회·수정·삭제 범위는 유지한다.
5. 서비스 워커는 기존 `push` 이벤트 처리와 알림 클릭 동작을 재사용한다. 성장 날짜를 URL에 담아 클라이언트가 성장일기로 이동시킨다.

## 성장 변경 데이터

클라이언트는 서버가 검증할 최소 필드만 보낸다.

```text
kind: created | updated | deleted
id: 기록 ID
babyId: 아기 ID
title: 기록 제목
date: YYYY-MM-DD
time: HH:MM 또는 빈 값
category: 허용된 성장일기 분류
height: 키
weight: 몸무게
head: 머리둘레
feedingType: 수유 종류
feedingMl: 수유량
feedingMinutes: 수유 시간
diaperKind: 기저귀 종류
```

수정·삭제는 현재 메모리 상태에서 변경 전 행을 찾아 제목·분류·날짜를 보완한다. 삭제 시에도 삭제 직전 정보로 알림을 만든다. 서버는 날짜·시간·분류·문자열 길이·숫자 범위를 다시 검증하고 허용되지 않은 필드는 무시한다.

## 알림 문구와 이동

- 추가: `수유 기록이 추가됐어요`
- 수정: `기저귀 기록이 수정됐어요`
- 삭제: `성장 기록이 삭제됐어요`
- 본문 예시: `8월 31일 10:20 · 분유 120ml`
- 알림 태그와 `dedupe_key`에는 기록 ID, 변경 종류, 발생 시각, 수신자 ID를 사용해 서로 다른 변경을 합치지 않는다.
- 알림 클릭 URL은 `growthDate`를 사용하며, 앱은 해당 날짜를 선택하고 성장일기로 전환한다.

## 일정 화면 제거

- `config.js`에서 `today-overview`와 `family-handoff` 모듈 등록을 제거한다.
- 해당 모듈의 JS·CSS 파일과 전용 테스트를 삭제한다.
- `family-utility.js`에서 더 이상 사용하지 않는 오늘 요약 함수와 관련 테스트를 제거하고, 검색 API는 남긴다.
- 기록 저장·할 일·검색·알림 모듈에는 제거된 전역 API 의존성이 남지 않아야 한다.
- 기존 설계 문서는 과거 결정 기록이므로 수정하지 않는다.

## 오류와 보안

- 푸시 발송 실패는 기록 저장 실패로 취급하지 않는다. 기존 일정 변경 알림과 동일하게 콘솔에 안전한 오류 코드만 남긴다.
- 현재 세션·가족 공간이 바뀐 뒤 도착한 비동기 결과는 알림을 보내지 않는다.
- 수신자 조회는 서버의 `household_id`와 기록자를 제외하는 조건으로 제한한다.
- 브라우저에는 anon/publishable key만 두고 service role key와 VAPID 비밀키는 Edge Function Secret에만 둔다.
- 알림 본문에는 성장 메모와 사진 경로를 넣지 않는다.

## 테스트 전략

- RED: 성장 기록 mutation 감지, 변경 전 행 보완, 성장 알림 payload/서버 정규화, `growth` 스키마 허용, 성장 날짜 이동에 대한 실패 테스트를 먼저 추가한다.
- GREEN: 기존 푸시 경로를 확장해 테스트를 통과시킨다.
- 제거 회귀 테스트는 두 모듈의 로더 참조·파일 참조·DOM 식별자가 없고 `family-utility` 검색 API가 계속 제공되는지 검증한다.
- 로컬 검증: 관련 Vitest 테스트, 전체 `npm test`, `npm run check`, `git diff --check`.
- Supabase 검증: migration 적용 상태, Edge Function 배포 상태, API 로그의 성공 응답을 확인한다.
- 공개 검증: 두 가족 기기 중 한 기기에서 성장·수유·기저귀 기록을 저장하고 다른 기기의 실제 푸시와 알림함, 성장일기 이동을 확인한다.

## 제외 범위

- 알림 설정 화면을 별도 종류별 토글로 분리하지 않는다. 기존 가족 일정 변경 알림 토글이 성장 기록 변경 알림도 포함하도록 문구만 갱신한다.
- 로컬 데모 모드에는 실제 가족 푸시를 보내지 않는다.
- 기록 저장 방식, RLS의 가족 데이터 접근 모델, 기존 일정 알림의 동작은 재설계하지 않는다.
