# 설정 하위 기능 요청 및 가족 일정 변경 푸시 설계

## 목표

1. 상단 내비게이션의 `요청` 탭을 제거하고 설정 화면에서 기능 요청 화면으로 진입한다.
2. 한 가족 구성원이 일정을 추가·수정·날짜 이동·삭제하면 변경한 사람을 제외한 같은 가족의 구독 기기에 즉시 푸시한다.
3. 아침 일정 브리핑이나 일정 시간 전 알림은 이번 범위에 포함하지 않는다.

## 화면 구조

- 상단 탭은 `일정 · 성장 · 동화 · 설정`과 권한이 있는 경우의 `관리`만 표시한다.
- 설정 화면에 `💡 기능 요청` 진입 카드를 둔다. 카드를 누르면 기존 기능 요청 작성·관리 화면을 연다.
- 기능 요청 화면에서는 상단 `설정` 탭을 활성 상태로 유지하고 `설정으로 돌아가기` 버튼을 제공한다.
- 설정 화면에 `🔔 가족 일정 변경 알림` 카드를 둔다. 현재 기기의 연결 상태와 `알림 받기` 또는 `알림 끄기` 동작만 제공한다.
- 아침 브리핑 시간, 브리핑 스위치, 일정 시간 전 알림 설정은 노출하지 않는다.

## 동작 및 데이터 흐름

### 기능 요청

1. `feature-request.js`는 독립 상단 탭을 만들지 않는다.
2. 설정 진입 카드가 기존 `featureRequestView`를 연다.
3. 기존 요청 저장, 가족별 분리, 관리자 상태 변경 로직은 유지한다.
4. `feature-request`가 저장된 과거 활성 화면 값은 복원하지 않고 설정 화면으로 정규화한다.

### 가족 일정 변경 푸시

1. 가족 구성원은 각 아이폰의 홈 화면 앱에서 한 번 `알림 받기`를 누른다.
2. 클라이언트는 알림 권한과 Web Push 구독을 받은 뒤 `push_subscriptions`에 `enabled=true`, `briefing_enabled=false`로 저장한다.
3. 일정 저장 성공 후 기존 `event-change-push.js`가 `daily-briefing-push` Edge Function의 `event-change` 액션을 호출한다.
4. 서버는 같은 `household_id`의 구성원 중 변경한 사용자를 제외하고 `enabled=true`인 구독에 즉시 발송한다.
5. 알림을 누르면 해당 일정 날짜의 캘린더를 연다.
6. 이 즉시 발송 경로는 Cron에 의존하지 않는다.

## 오류와 안전 경계

- iPhone에서 홈 화면 앱이 아니면 설치 안내를 표시하고 권한 요청을 시도하지 않는다.
- 사용자의 직접 탭에서만 알림 권한을 요청한다.
- 로그인 또는 가족 공간이 없으면 구독을 만들지 않는다.
- 구독과 발송은 항상 `household_id`와 인증 사용자로 범위를 제한한다.
- 발송 실패가 일정 저장을 실패시키지는 않되, 설정 카드에는 연결 실패 원인을 표시한다.
- 푸시 endpoint와 키는 UI, 로그, Git에 노출하지 않는다.

## 구현 범위

- 기존 Web Push, Service Worker, Edge Function, `push_subscriptions` 테이블을 재사용한다.
- 새로운 외부 의존성은 추가하지 않는다.
- 일정 변경 푸시를 켜기 위해 아침 브리핑을 먼저 켰다가 끄는 우회 동작은 만들지 않는다.
- DB 스키마 변경은 하지 않는다. 운영 환경의 VAPID 설정은 값 노출 없이 상태만 검증한다.

## 검증

- 상단에 `요청` 탭이 생성되지 않는 테스트
- 설정의 기능 요청 진입과 설정 활성 상태·복귀 동작 테스트
- 구독 시 `enabled=true`, `briefing_enabled=false` 전송 테스트
- 일정 추가·수정·이동·삭제가 다른 가족만 대상으로 하는 기존 테스트 유지
- 화이트·다크 모바일 폭에서 두 설정 카드와 기능 요청 화면 확인
- 운영에서 가족 기기 두 대를 구독한 뒤 A가 일정을 변경하고 B만 푸시를 받는 실제 종단 테스트
