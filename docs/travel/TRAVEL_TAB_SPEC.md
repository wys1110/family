# 우리 가족 여행 탭 — 제품·기술 설계 v1

작성: 2026-09-21 · 구현 담당: Luna · 상태: 설계 확정안, 구현/배포 전

## 1. 목표와 범위

여행 날짜와 가족 인원을 한 번 입력하고 항공·숙소 후보, 예약 현황, 날짜별 일정, 지도 동선, 준비물, 여행 기록을 한 여행 안에서 관리한다. 스카이스캐너의 비교 경험과 마이리얼트립의 여행 관리 경험을 참고하되 기존 Nova 디자인을 유지한다.

핵심 여정: **여행 만들기 → 항공·숙소 찾기 → 후보 비교 → 예약처에서 예약 → 예약 등록 → 일정·지도 편집 → 여행 중 확인 → 추억 기록**.

| 구분 | 1차 출시 | 후속 확장 |
|---|---|---|
| 여행·가족 공유 | 여행 생성, 동행인, 날짜, 가족 공동 편집 | 여행별 외부 초대 |
| 항공·숙소 | 외부 검색 열기, 링크·가격 수동 저장, 나란히 후보 비교 | 제휴 API 실시간 통합 검색·가격 재확인 |
| 예약 | 예약처로 이동, 사용자가 완료 상태·정보 등록 | 제공처가 허용하는 예약 상태 조회 |
| 일정·지도 | 날짜별 장소, 순서, 지도 핀, 도로 경로·길찾기 | 이동 순서 추천, 혼잡 반영 |
| 준비·기록 | 체크리스트, 지출, 사진·메모 | 예약서 OCR, 회고 자동 초안 |
| 결제·발권 | 외부 예약처에서 진행 | 앱 내 결제·발권은 별도 사업 범위로 재설계 |

**중요:** 외부 검색 링크만으로 앱 내 실시간 최저가가 구현되지는 않는다. 1차 검색 화면의 문구는 `예약처에서 검색`; API 연동된 제공처만 `앱에서 가격 비교`로 표시한다. 미연동 공급자에 가짜 가격·임의 딥링크를 붙이지 않는다. 링크를 눌렀다는 사실은 예약 완료의 증거가 아니다.

## 2. 정보 구조와 화면

최상위 탭: 일정 / 성장 / **여행** / 동화 / 설정 / 관리(권한 있는 사용자).

모바일은 탭을 한 줄 가로 스크롤로 표시하고 각 터치 영역은 최소 44px. 활성 탭이 가려지면 탭 영역 안에서만 보이게 이동한다. 페이지 전체 가로 넘침이나 기존 화면의 스크롤 초기화는 금지한다.

여행 탭 첫 화면에는 진행 중·예정·지난 여행 카드와 `새 여행` 버튼을 둔다. 카드에는 목적지, 날짜, D-day, 예약 완료 개수, 준비 완료 개수만 표시한다. 큰 장식 이미지 때문에 핵심 정보가 밀리지 않게 한다.

여행 상세의 내부 메뉴: **요약 / 예약 / 일정·지도 / 준비 / 기록**. 예산 요약은 요약, 실제 지출 편집은 기록 안에 둔다.

| 화면 | 주요 내용 | 대표 동작 |
|---|---|---|
| 새 여행 | 여행명, 출발지, 목적지, 날짜, 성인·아동·유아, 객실, 선택 예산 | 여행 만들기 |
| 요약 | 날짜·날씨 대신 초기에는 날짜만, 항공·숙소 확정 현황, 오늘 일정, 준비할 일, 예상/지출 금액 | 예약 찾기 / 일정 이어서 짜기 |
| 예약 | 공통 검색 조건 + 항공/숙소 전환, 후보함, 예약 현황 | 후보 저장 / 비교 / 예약처 열기 |
| 일정·지도 | 날짜 선택, 시간순 카드, 번호 핀, 이동 구간 | 장소 추가 / 순서 변경 / 길찾기 |
| 준비 | 출국·아기·짐·교통 체크리스트, 담당자·기한 | 완료 체크 |
| 기록 | 날짜별 사진·메모, 지출, 다녀온 장소 | 사진·메모 남기기 |

### 모바일 상세 배치

1. 상단: 뒤로가기, 여행명, 더보기.
2. 날짜·동행인 한 줄. 여행 전체 정보를 펼쳐 수정 가능.
3. 내부 메뉴. 선택 상태 유지.
4. `일정·지도`에서는 날짜 칩 → 지도(높이 약 240px, 전체화면 버튼) → 해당 날짜 일정 카드 순서. `일정만` 모드도 제공한다.
5. 장소 추가 버튼은 콘텐츠 흐름 안에 배치한다. 지도 출처 표기나 마지막 카드를 가리지 않는다.
6. 일정 카드를 누르면 해당 핀 강조. 핀을 누르면 카드 위치로 이동하되 열려 있던 입력 초안은 유지한다.

데스크톱 1024px 이상: 일정 목록 40% / 지도 60% 분할. 지도는 패널 안에서 유지한다. 320·390·768·1440px, 밝음/어두움 모두 검사한다. 색상은 기존 `--nova-*` 변수만 사용한다.

### 상태 디자인

빈 여행: `날짜부터 정해볼까요?` + 생성 버튼. 검색 로딩: 카드 스켈레톤. 부분 실패: 항공 결과는 유지하고 숙소 영역만 재시도. 지도 실패: 일정·주소·외부 길찾기는 계속 이용 가능. 저장 실패: 입력 내용을 남기고 `저장되지 않음` 표시. 사진 밝기·색상 필터 추가 금지.

## 3. 날짜 입력과 항공·숙소 비교

공통 조건은 여행에 저장하되 항공 날짜와 숙소 체크인/체크아웃을 별도로 조정할 수 있다. 자정 도착이나 마지막 날 야간 출발 때문에 숙박 날짜를 왕복 항공 날짜에 자동 고정하지 않는다.

- 출발 공항/도시, 목적지 공항/지역을 구분한다. 도시 이름을 IATA 코드로 추정하지 않는다.
- 출국·귀국 날짜, 성인 수, 아동·유아 정보, 좌석 필요 여부, 객실별 투숙객, 통화.
- 아동 나이는 항공 출발일/숙소 체크인일 기준으로 계산하며 제공처 연령 정책을 따른다. 기존 아기 프로필 연결은 선택. 생년월일 외부 전송은 공급자가 실제 요구하는 경우만 처리한다.
- 필터: 직항, 출발 시간, 수하물 포함, 무료 취소 여부, 숙소 위치, 객실/침대 구성, 아기 침대 등. 아기 시설이 확인되지 않으면 `정보 없음`; 자동으로 있음 처리하지 않는다.
- 항공 카드는 가족 전체 왕복 총액인지 편도·1인 금액인지 명시하고 수하물/유아요금/수수료 포함 여부를 보여준다.
- 숙소 카드는 총 숙박일·객실 수·가족 인원 기준 총액과 세금/현장 결제 포함 여부를 보여준다.
- 항공 후보 최대 3개, 숙소 후보 최대 3개 비교. 조합 비용은 선택한 두 후보 합계이며 **패키지 할인 가격이 아님**을 표시한다.
- 통화가 다르면 환율 출처·시각이 있을 때만 참고 환산. 없으면 통화별로 분리한다. 환산액을 결제 확정액으로 표시하지 않는다.
- 가격마다 `조회 시각`, `공급자`, `직접 입력/조회 가격`, 유효성 상태를 표시한다. 가격 유효 시간은 공급자 정책에 맞춘다.
- 여행 날짜·인원·객실 변경 시 이전 후보를 삭제하지 않고 `이전 조건의 후보`로 구분한다. 재검색 없이 현재 조건의 최저가로 재사용 금지.

### 외부 연동 전략

| 기능 | 설계 선택 | 전제/실패 시 처리 |
|---|---|---|
| 항공·숙소 실시간 | Skyscanner 공급자 어댑터 우선 검토 | 제휴 심사와 API 키가 있어야 활성화 |
| 숙소 대안 | Booking.com Demand 어댑터 | Managed Affiliate 자격·계약·접근 권한 필요 |
| 1차 예약 이동 | 검증된 HTTPS 제공처 링크 | 공식 검색 파라미터가 확인되지 않으면 홈페이지 + 조건 복사 |
| 지도·장소 | Google Maps JavaScript + Places 계열 | API 설정·결제 계정·허용 API·도메인 제한을 배포 전에 준비 |
| 도로 동선 | Routes 공급자, 자동차/도보 우선 | 지원 안 되는 지역·교통수단은 외부 길찾기 안내 |
| 지도 없는 상태 | 주소·장소 목록 + Google Maps URL | Maps URL은 API 키 없이 사용 가능, 앱 내 지도와는 별도 |

가격 API 승인 전에도 후보 저장과 여행 관리 기능은 완성한다. 다만 **실제 지도의 모든 핀·동선을 함께 보는 기능은 지도 공급자 연결이 완료되어야 출시 완료로 인정**한다. 키 없는 데모 지도만으로 완료라고 보고하지 않는다.

API 응답은 서버에서 정규화한다. 제공처 API 키를 GitHub Pages/브라우저 번들에 넣지 않는다. 지도 브라우저 키는 공개 노출을 전제로 HTTP referrer 및 API 제한을 적용하고, 서버 키와 분리한다. 유료 서비스 가입·결제 활성화는 사용자 승인을 받아 진행한다.

## 4. 예약 모델과 여행 일정 연결

후보 상태와 실제 예약 상태를 별도로 관리한다.

- 후보: `saved → shortlisted → dismissed`; 선택 변경 가능.
- 예약: `planned → booked → cancelled`, 필요 시 `completed`. `booked`는 사용자가 확인하여 등록한 경우 `manual` 출처를 기록한다. 후속 API 검증은 `provider_verified`로 구분한다.
- `예약처 열기` 클릭은 클릭 이력만 남기며 booked로 바꾸지 않는다.
- 예약 등록 항목: 종류(항공/숙소/렌터카/체험/기타), 제공처, 상품명, 예약 날짜·현지 시간, 인원, 금액·통화, 링크, 선택 메모, 취소 기한.
- 1차에서는 여권·결제카드·예약 확인 코드·바우처 원문 업로드를 요구하지 않는다. 여행 사진은 예약 서류 업로드와 분리한다.
- 항공 등록 시 출발/도착 일정, 숙소 등록 시 체크인/체크아웃 일정을 생성하겠다는 미리보기를 보여준다. 승인 후 같은 예약 ID로 upsert하며 중복 생성하지 않는다.
- 날짜 변경·예약 취소는 연결 일정 변경안을 먼저 보여준다. 기록·과거 일정은 자동 삭제하지 않는다.
- 기존 가족 캘린더 연동은 2차 옵션. `여행 기간만 캘린더에 추가`를 기본으로 제안한다. 사용자가 선택한 상세 일정만 단방향 동기화하며, 중복 키와 수동 편집 충돌 처리가 있어야 한다.

## 5. 일정·지도·동선 규칙

일정 종류: 방문 / 식사 / 이동 / 숙박 / 휴식 / 수유·기저귀 메모 / 자유 메모. 여행의 아기 돌봄 일정은 계획이며 성장일기의 실제 수유 기록으로 자동 복사하지 않는다.

- 장소 검색 또는 직접 입력으로 추가. 저장 전 위치를 지도에서 확인한다. 좌표 없는 메모도 저장 가능하며 지도에서는 제외하고 목록에 표시한다.
- 일정은 날짜, 순번, 제목, 선택 시간·소요시간, 장소, 이동수단, 메모를 가진다.
- 순서 변경: 드래그 + 위/아래 이동 버튼. 키보드·터치 모두 가능. 날짜 간 이동 시 원래 시간을 유지할지 묻는다.
- 시간이 확정된 예약은 고정 표시. 순서 변경이 예약 시간을 자동 변경하지 않는다.
- `전체 여행`은 날짜별 색상과 범례, `하루`는 1·2·3 번호 핀. 비행 구간은 별도 점선과 비행 아이콘으로 표시하고 자동차 도로 경로와 섞지 않는다.
- 경로 계산 전 좌표를 연결한 선은 `방문 순서` 점선. Routes 응답이 있는 구간만 실제 이동 경로로 표시한다. 직선 거리를 운전 시간으로 변환하지 않는다.
- 경로 응답에는 거리·예상 소요시간·교통수단·계산 시각·제공처를 표시한다. 교통 상황과 휴식은 달라질 수 있다.
- `이동시간 + 체류시간`을 다음 일정 시작과 비교하여 겹침만 알린다. 시간을 모르면 충돌 없음으로 확정하지 않는다.
- 휴식 간격·하루 방문 수·하루 이동시간은 가족이 설정할 수 있다. 의학적 적정 수유/수면 간격을 추정하지 않는다.
- 순서 추천은 2차: 고정 항공·예약·숙박을 보존하는 변경안만 제시하고 사용자가 적용한다.
- 외부 길찾기는 한 구간씩 제공한다. 여러 경유지 URL은 모바일 경유지 제한을 확인하고 잘라 제공한다.
- 현 위치 권한은 `내 위치`를 눌렀을 때만 요청. 거부 시 저장한 장소 중심으로 동작한다.

## 6. 준비·예산·추억

준비 템플릿: 아기 여권 준비 여부, 항공 유아 등록 확인, 숙소 아기 침대 확인, 카시트, 유모차, 수유용품, 보험 확인, 공항 이동. 여권 번호나 신분증 사본을 저장하지 않는다. 실제 여행 요건은 별도 확인하도록 항목만 제공한다.

항목 필드: 제목, 카테고리, 담당 가족 구성원, 선택 기한, 완료 상태. 체크리스트는 여행별로 독립한다. 기존 가족 할 일에 넣는 기능은 사용자의 선택으로 후속 제공하고 복제 출처를 남긴다.

예상 비용은 후보/계획 기준, 확정 비용은 예약 기준, 실제 지출은 지출 원장 기준으로 분리한다. 예약에 연결된 지출은 원장 합계에 한 번만 반영하고 예약 총액과 중복 가산하지 않는다. 취소 예약도 환불 확정 전에는 지출을 지우지 않는다. 환불은 원장에 연결된 음수 거래로 기록한다.

추억: 여행일별 사진·메모, 연결 장소, 하이라이트. 사진은 기존 썸네일/지연 로딩 패턴을 재사용한다. 여행 완료는 사용자 선택으로 보관 상태로 전환하고 수정 가능하게 유지한다. 날짜가 지났다는 이유만으로 완료 처리하지 않는다.

## 8. 데이터 계약

아래는 논리 스키마이며 실행할 SQL이 아니다. 모든 가족 데이터에 `household_id`, `created_by`, `created_at`, `updated_at`, 낙관적 잠금용 `version`을 둔다. PK는 UUID. 날짜는 ISO date, 실제 시각은 timestamptz와 IANA timezone을 함께 보존한다.

| 테이블 | 핵심 필드/관계 |
|---|---|
| `travel_trips` | id, household_id, title, origin, destination_label, start_date, end_date, default_timezone, currency, budget_minor?, status(planning/booked/travelling/completed/archived), search_revision |
| `travel_travelers` | id, trip_id, 표시 이름, household member/baby 참조?, 생년월일?(필요한 아동만), 좌석 필요 여부, room_group; 가족 내 공유 범위 명시 |
| `travel_candidates` | id, trip_id, kind(flight/stay/activity/car), provider, source(manual/api), title, booking_url, normalized_details, amount_minor?, currency?, quoted_at?, expires_at?, search_revision, status |
| `travel_bookings` | id, trip_id, candidate_id?, kind, provider, title, start_at?, end_at?, start_timezone?, end_timezone?, local_checkin_date?, local_checkout_date?, status, confirmation_source, amount_minor?, currency?, cancel_deadline_at?, url?, note? |
| `travel_places` | id, trip_id, user_label, user_address?, user_latitude?, user_longitude?, provider?, provider_place_id?, source(user/provider); 사용자 입력과 공급자 콘텐츠 구분 |
| `travel_items` | id, trip_id, local_date, position, kind, title, place_id?, start_at?, end_at?, timezone?, duration_minutes?, transport_mode?, booking_id?, booking_event_role?, fixed_time, note? |
| `travel_tasks` | id, trip_id, category, title, assignee_user_id?, due_date?, completed_at? |
| `travel_expenses` | id, trip_id, booking_id?, category, amount_minor(음수 환불 가능), currency, spent_at, refund_of_id?, note? |
| `travel_memories` | id, trip_id, item_id?, local_date, title?, note? |
| `travel_media` | id, trip_id, memory_id, private_storage_path, thumbnail_path?, mime_type, byte_size, position |

- 각 하위 테이블의 (trip_id, household_id)는 trips(id, household_id)에 복합 FK. 다른 가족의 여행 ID/장소/예약/사진을 교차 연결하지 못하게 한다.
- place_id/candidate_id/booking_id/item_id 같은 참조는 동일 trip에 속함을 복합 FK 또는 서버 제약으로 검증한다. created_by·household_id·trip_id 변경으로 소유 범위를 바꾸지 못하게 한다.
- end_date ≥ start_date, 실제 end_at ≥ start_at, position·duration 범위, 좌표 범위, 제목/메모 길이, URL scheme, 통화 코드 검증.
- booking_id + booking_event_role은 여행별 unique. 항공 출발/도착, 숙소 체크인/체크아웃 중복 방지.
- 저장 후보는 API 전체 원문 복사가 아니라 최소 정규화 필드만 저장한다. 공급자 보관 조건이 허용하지 않으면 토큰/ID만 보존하고 조회 시 재요청한다.
- Google place ID와 사용자가 작성한 장소·메모를 구분한다. 공급자 좌표·명칭·사진·리뷰·경로 결과는 사용권·캐시 조건 확인 없이 영구 저장하지 않는다. 사용자 좌표만 별도로 영구 보관한다.
- 비용은 float가 아닌 통화 최소 단위 정수와 통화 코드. JPY/KRW/USD 소수 자릿수 차이 반영.
- 날짜 없는 메모를 임의로 오늘 일정에 넣지 않는다. 방문 날짜가 없으면 `보관함` 후보로 유지한다.

### 저장/동시 편집

일반 편집은 명시적 저장 버튼. 체크·순서 이동은 낙관적으로 표시하고 실패 시 되돌린다. 동시 수정은 version 조건으로 감지하고 덮어쓰지 말고 새 버전 불러오기/변경 비교를 제시한다. 일정 순서 변경은 트랜잭션 RPC로 해당 날짜 전체 순서를 원자적으로 바꾸고 멱등 요청 ID를 사용한다.

온라인 가족 공유를 우선한다. 오프라인에서는 민감한 여행 데이터를 새 영구 캐시에 저장하지 않고 현재 열린 일정의 열람과 메모리상의 초안만 지원한다. 저장되지 않은 초안은 이탈 전 알린다. 공급자 지도 타일을 service-worker에서 캐시하지 않는다.

### RLS·사진·백업

기존 `public.is_household_member(household_id)`와 실제 household_members를 기준으로 SELECT/INSERT/UPDATE/DELETE 정책을 설계한다. UPDATE에는 USING/WITH CHECK 모두 필요하다. anon 직접 접근 금지. 사용자 수정 가능한 JWT user_metadata로 권한 판단 금지. 서버 프록시는 인증뿐 아니라 trip 소속 검증까지 수행한다.

사진은 비공개 버킷 `household/trip/memory/...` 경로 및 Storage 정책을 적용하고 서명 URL은 짧게 사용한다. 파일 형식·실제 이미지 여부·크기 검증, 썸네일 생성, 사진 위치 메타데이터 제거를 검토한다. 서비스 키는 클라이언트 금지.

기존 가족 데이터 내보내기/백업에 여행 테이블·사진 참조를 포함하는 확장을 출시 체크리스트에 넣는다. 복원 시 ID 매핑과 가족 범위 검증, 중복 방지를 적용한다. 전체 백업 호환성이 끝나기 전에는 여행 전용 JSON 내보내기를 제공하고 기존 백업에 포함되는 것처럼 표시하지 않는다.

## 9. 서버와 공급자 인터페이스

인증된 호출 예시이며 특정 공급자 API 경로를 그대로 복제하지 않는다.

- `searchTravel({tripId, revision, kind, criteria, cursor?})` → `{status, offers, nextCursor?, fetchedAt, warnings, capability}`.
- `recheckOffer({tripId, candidateId})` → `{availability, total, currency, bookingUrl, checkedAt, changedFields}`.
- `routeDay({tripId, localDate, revision, mode, itemIds})` → `{segments, warnings, computedAt}`. 각 segment는 from/to ID, distanceMeters?, durationSeconds?, geometry?, source, status.
- `capabilities()` → flights: external/live, stays: external/live, map: unavailable/interactive, routing: unavailable/available. 미연동 버튼도 상태에 맞게 설명한다.

검색은 항공/숙소 독립 요청, 취소 가능, 공급자별 타임아웃·제한된 재시도·요청 중복 제거. 항공 create/poll 흐름이면 어댑터 내부에서 세션 상태를 관리한다. 오래된 revision의 결과가 새 결과를 덮어쓰지 못하게 한다. 한 제공처 실패가 여행 화면 전체를 막으면 안 된다.

외부 URL 가져오기/스크래핑은 1차 범위 밖. 사용자 URL은 HTTPS 허용 검증 후 링크로만 취급하고 HTML로 렌더링하지 않는다. 서버 임의 URL fetch를 추가하지 않는다. 제공처 딥링크는 허용 도메인을 검증하고 새 창은 noopener/noreferrer 적용한다.

지도/검색은 가족별 호출 제한과 서버 예산 상한을 둔다. 지도 이동/드래그 중에는 경로 API를 계속 호출하지 않고 순서 저장 후 또는 `동선 계산` 클릭 후 실행한다. 원시 개인정보·후보 조회 응답 전체를 로그에 남기지 않는다.

9. 모바일 지도 드래그와 페이지 스크롤이 충돌하지 않음; 카드 마지막 버튼과 지도 출처 가림 없음.
10. 여행 탭을 열기 전 지도 SDK·검색 API·여행 상세 사진 요청 0. 앱 최초 진입 속도 회귀 측정.
11. 기존 일정·성장·동화·설정·관리 및 알림 기능 회귀 테스트 통과.
12. 공급자 연동 없는 상태는 명확한 대체 UI. 실제 가격·지도·예약 확인으로 오인할 데모 데이터 없음.

## 11. 근거와 연결 준비물

2026-09-21 공식 문서 확인. API 자격 획득·개인 계정 승인 여부는 미확인이다.

- [Skyscanner 인증](https://developers.skyscanner.net/docs/getting-started/authentication): API 접근은 파트너십 심사와 키가 필요하고 클라이언트에 키를 노출하지 말아야 한다.
- [Booking.com Demand 사전 요건](https://developers.booking.com/demand/docs/getting-started/prerequisites): Managed Affiliate, 계약 후 Partner Centre, API 토큰/affiliate ID가 요구된다.
- [Google Maps URLs](https://developers.google.com/maps/documentation/urls/guide): 외부 지도 검색·길찾기 연결은 API 키 없이 가능하다. 경유지는 실행 환경별 제한을 확인한다.
- [Google Routes 사용·결제](https://developers.google.com/maps/documentation/routes/usage-and-billing): 지도 SDK와 경로 API의 과금/쿼터를 별도로 확인한다.
- [Google Maps 보안](https://developers.google.com/maps/api-security-best-practices): 브라우저와 서버 키를 분리하고 사용처와 API를 제한한다.
- [Google Maps 정책](https://developers.google.com/maps/documentation/javascript/policies): 제공처 표기와 콘텐츠 저장 제한을 지키고 place ID와 사용자 작성 데이터를 분리한다.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): 노출 테이블의 행 접근 정책을 적용한다.

Luna가 요청할 설정: 지도 공급자 프로젝트와 제한된 키, 서버 프록시 secret 설정, 공급자 제휴 승인 여부. 비밀키는 대화·문서·Git 저장소에 붙여넣게 하지 말고 서비스의 secret 설정으로 받는다. 가격 API 승인 전에는 PR 1~3을 진행한다.
