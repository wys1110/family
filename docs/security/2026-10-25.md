## 6. AI 출처 URL의 리디렉션 사전 검증 — 수정

- 심각도: 중간의 조건부 SSRF 위험. 신뢰한 Google/YouTube 응답이 비허용 주소로 리디렉션해야 한다. 실제 제공자의 악용 가능한 리디렉션이나 운영 내부망 접근을 입증한 것은 아니다.
- 근거: 기존 `supabase/functions/baby-ai/sources.ts:50`은 Google URL을 HEAD + redirect:follow로 요청한 뒤 response.url을 검사했다. YouTube oEmbed/채널 요청도 기본 자동 리디렉션이었다. 사후 거부는 이미 발생한 네트워크 요청을 취소하지 못한다. 수정 전 운영 버전 7의 6개 소스 파일이 로컬 HEAD와 정확히 같음을 확인했다.
- 재현: 초기 신뢰 URL만 자체 loopback HTTP 서버로 연결한 테스트 어댑터에서 실제 Fetch를 사용했다. 서버가 자체 `/private`로 보내는 302를 반환하자 기존 코드는 해당 경로에 1회 요청한 뒤 결과를 버렸다. 수정 후 요청은 0회였다. 실제 메타데이터 서비스나 다른 시스템은 호출하지 않았다.
- 수정: Google·YouTube의 모든 fetch를 공통 사전 검증 경로로 처리. 매 단계 HTTPS/기존 허용 호스트를 확인하고 사용자정보·비표준 포트가 있는 URL을 거부한다. 자동 추적 대신 Location을 읽어 다음 주소를 검사한다. 상대 경로는 지원하며 요청 수는 5회, 체인 전체 신호는 3초 제한이다. 신뢰 목록 밖의 중간 경유지는 거부한다.
- 검증: 실제 HTTP 재현과 모의 리디렉션, IPv4/IPv6 loopback·메타데이터 주소·위장 도메인·다른 포트·사용자정보·YouTube 2단계·정상 공식 URL·순환 제한을 포함해 출처 테스트 17개 통과. 전체 130개 파일/802개 테스트, npm run check 통과.
- 운영 반영: baby-ai Edge Function 버전 8 ACTIVE. 내려받은 배포 파일 6개가 적용한 파일과 일치했다. 기존 함수 내부 JWT/cron 인증과 verify_jwt=false 설정을 유지했고, 배포 후 인증 없는 POST가 401 UNAUTHORIZED임을 확인했다. 실제 가족 기록을 보내거나 AI 생성을 요청하지 않았다.
- 한계: 합법적인 출처라도 허용되지 않은 중간 도메인을 경유하면 제외될 수 있다. 허용 도메인 자체의 DNS/서버 장악까지 방어하지는 않는다. 로그인한 실제 AI 생성과 현재 Google 리디렉션 URL의 실사용은 별도 검증이 필요하다.
- 참조: [OWASP SSRF 예방 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)의 자동 리디렉션으로 입력 검증이 우회되는 위험.
- 프런트엔드 조사: 여행 카카오 링크는 고정 HTTPS 호스트와 인코딩한 장소명/숫자 좌표로 생성하고, 챗봇 답변은 textContent를 사용함을 확인했다. innerHTML/URL 후보 199곳의 전체 XSS 감사를 완료한 것은 아니다. 서비스워커 알림 목적지와 로컬 기록 표시 경로는 후속 점검한다.

## 7. 알림 이동 주소와 기존 창 선택 — 수정

- 심각도: 낮음, 이동 범위 제한 및 방어 보강. 알림 서버는 현재 `./?eventDate=…`, `./?growthDate=…`, `./?briefingDate=…` 형태를 생성한다. 일반 사용자가 임의 푸시 URL을 주입할 수 있다는 경로는 확인하지 않았다.
- 근거: 기존 service-worker.js:103은 notification.data.url을 검증 없이 openWindow/navigate에 전달했다. 잘못된 URL이면 waitUntil 이전에 예외가 발생했다. :106의 기존 창 선택은 origin만 비교하여 같은 GitHub Pages 도메인의 다른 앱도 선택했다.
- 재현: 실제 서비스워커 코드를 VM에서 실행한 이벤트 테스트에서 다른 앱 창이 먼저 목록에 있으면 그 창을 가족 앱으로 이동시키는 것을 확인했다. 기존 코드에서 창 선택 테스트 2개 실패, 수정 후 통과. 실제 사용자의 창은 이동시키지 않았다.
- 수정: push 수신과 notificationclick 양쪽에서 가족 앱 진입 페이지(`/family/` 또는 `/family/index.html`, 루트 배포도 지원)만 허용한다. 기존 query/hash 링크는 보존한다. 외부 origin, 다른 경로, 사용자정보가 있는 URL, 비문자열·잘못된 URL은 홈으로 복귀한다. 저장된 이전 알림도 클릭할 때 다시 검사한다. 같은 도메인의 다른 앱 창은 건드리지 않는다.
- 검증: 외부 링크, 프로토콜, 경로 우회·인코딩, 깨진 URL, 유효한 일정/성장/브리핑 링크, 다른 앱 창 보존, 루트 배포, 빈 알림 본문 보존을 포함한 이벤트 테스트 21개 추가. 전체 131개 파일/823개 테스트, npm run check 통과.
- 한계: VM의 URL 파서와 이벤트/WindowClient 대역으로 검사했다. 실제 iPhone 푸시 클릭, 설치된 서비스워커의 즉시 교체까지 확인한 것은 아니다. 기기에 적용되려면 다음 서비스워커 업데이트가 필요하다.
