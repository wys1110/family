## 3. 공동 기록 작성자·가족 소속 변경 — 수정 (추가 점검)

- 심각도: 중간, 기록 무결성. 외부인이 다른 가족을 읽을 수 있다는 취약점은 확인하지 않았다.
- 근거: app.js:554, :556, :574의 upsert 변환은 수정 시에도 현재 사용자를 created_by로 보낸다. 운영 DB events/babies/growth_entries UPDATE 정책은 가족 멤버십만 검사하고 기존 작성자를 고정하지 않았다. family_todos는 작성자 변경은 차단하지만 가족 소속은 고정하지 않았다.
- 영향: 공동 수정 시 원래 작성자가 바뀔 수 있고, 두 가족 모두에 속한 사용자가 공유 기록을 다른 가족으로 옮길 수 있었다. UUID를 아는 것만으로 외부 가족 기록을 수정하는 경로는 확인되지 않았다.
- 수정: `supabase/migrations/20261025085332_preserve_family_record_identity.sql:2`의 공통 invoker 트리거를 4개 테이블에 적용. 작성자는 이전 값을 유지하며 household_id 변경은 거부한다. 기존 upsert를 사용하는 이전 앱도 공동 수정이 가능하다. 과거에 바뀐 작성자를 추정해 복원하지 않는다. 신규 설치용 schema.sql:456에도 같은 보호를 포함했다.
- 검증: 기존 정책을 재현한 로컬 DB에서 보호 로직 없이 작성자/소속 테스트가 실패함을 확인한 뒤 적용해 통과. 외부인 읽기/수정 차단, 신규 작성자 위조 차단, 비공개 할 일, 공동 upsert를 포함한 6개 회귀 테스트 추가. 전체 129개 파일/771개 테스트와 npm run check 통과.
- 운영 검증: migration 적용 후 authenticated 역할로 가상 일정의 다른 가족 구성원 공동 upsert가 성공하고 원래 작성자가 보존되는지 assert로 확인, 전체 트랜잭션 rollback. 실제 가족 기록 변경 없음. 새 함수에 대한 보안 advisor 경고 없음.

## 4. 배경사진 파일의 소유자 권한 우회 — 수정 (저장소 점검)

- 심각도: 중간, 같은 가족의 일반 구성원에 의한 파일 무결성/가용성 침해. 외부 가족의 사진 열람 우회는 확인되지 않았다.
- 근거: `supabase/migrations/20260810005856_household_wallpapers.sql:18`은 배경사진 메타데이터 변경을 소유자에게 제한하지만, `20260715_growth_records_and_photos.sql:28`의 파일 정책은 가족 멤버십만 확인했다. 운영 DB도 동일했다. `app.js:733`은 배경사진을 `<가족 UUID>/wallpapers/<화면>/…` 경로에 저장한다.
- 영향: 일반 구성원이 Storage API를 직접 호출하면 소유자의 배경사진 파일을 덮어쓰거나 지울 수 있었다. 화면의 권한 또는 메타데이터 테이블 정책만으로 파일 변경을 막을 수 없다.
- 수정: `supabase/migrations/20261025090311_protect_wallpaper_objects.sql:2`에서 INSERT/UPDATE/DELETE 정책에 wallpapers 경로의 소유자 검사를 추가. UPDATE는 원래 경로와 새 경로 모두 검사하여 폴더 밖으로 이동하거나 일반 사진을 배경사진 경로로 이동하는 우회도 차단한다. 신규 설치 schema.sql:291에도 반영했다. 가족의 SELECT와 일반 성장사진/백업 사진 공동 관리는 유지한다.
- 재현/검증: 기존 정책만 실행하면 덮어쓰기, 수정, 배경사진 폴더로 이동 차단 테스트 3개가 실패했다. 수정된 마이그레이션과 신규 설치 정책 각각에 대해 7개, 총 14개 테스트가 통과했다. 소유자 업로드/upsert/수정/삭제, 가족 열람, 외부인 및 다른 버킷 접근 차단도 포함한다. 전체 130개 파일/785개 테스트, npm run check 통과.
- 운영 검증: 마이그레이션 적용 후 실제 비소유자 구성원의 authenticated 역할로 가족 배경사진 SELECT가 1개 이상이며 UPDATE 대상이 0개인 것을 assert로 확인하고 트랜잭션 rollback. 이름을 그대로 지정하는 UPDATE였으며 실제 파일을 업로드하거나 삭제하지 않았다. 운영 카탈로그에서 네 가지 정책과 UPDATE 양쪽 검사를 다시 확인했다.
- 한계: Storage HTTP 업로드·삭제와 실제 휴대폰 조작은 별도로 실행하지 않았다. 이미 발급된 서명 URL의 만료 전 접근, 잘못된 경로 입력 처리, 전체 사진 보관/삭제 정책은 후속 점검 대상이다.
- 근거 문서: [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control). 기존 권한과 호출 경로를 대조한 뒤 저장소 정책을 수정했다.

## 5. 육아 챗봇·CLI 실행 경계 — 새 취약점 미재현, 회귀 검증 보강

- 범위: `scripts/parenting-codex-server.mjs:22`의 CLI 인자, `:34`의 spawn, `:53`의 표준 입력, HTTP Host/Origin/token 및 파일 경로 검사, 큐 claim/finish의 작성자·lease·현재 가족 멤버십 검사. 프로덕션 동작을 바꾸는 수정은 하지 않았다.
- 실제 실행: 설치된 Codex CLI 0.145.0과 앱의 askCodex를 통해 무작위 표식을 담은 임시 가상 파일을 읽으라는 질문을 전송했다. 파일 내용은 질문에 포함하지 않았다. 답변은 파일/셸을 사용할 수 없다는 안내였고 표식은 노출되지 않았다. 가상 파일은 finally에서 삭제했다. 실제 가족 기록이나 비밀 파일을 요청하지 않았다. 이 한 번의 결과는 모든 프롬프트 주입에 안전하다는 증거가 아니다.
- HTTP 검증 추가: 실제 loopback 서버에서 공개 파일은 열리고 부모 경로·URL 인코딩·루트와 이름이 비슷한 형제 폴더·파일/디렉터리 심볼릭 링크를 통한 외부 파일 접근은 404임을 확인한다. 실패 응답에 파일 내용이나 로컬 경로를 포함하지 않는다. 요청 연결 종료 시 inference AbortSignal이 전달되고 다음 요청이 처리되는지도 검증한다.
- 큐 검증 추가: 두 유효한 워커 키가 각각 자신의 질문만 claim하며, 상대의 실제 lease까지 알아도 상대 답변을 finish할 수 없는지 확인한다. claim 후 가족 탈퇴 시 finish/조회가 거부되고, 만료 정리 시 임시 기록·lease가 삭제되는 것도 확인한다.
- 검증: 4개 회귀 테스트 추가. 전체 130개 파일/789개 테스트 및 npm run check 통과. 큐 검증은 실제 마이그레이션 SQL을 실행한 로컬 PostgreSQL 호환 테스트이며 운영 계정/워커를 새로 등록하지 않았다.
- 잔여 범위: 모든 CLI 도구가 향후 버전에서도 비활성화되는지, OpenAI 측 보관 정책, 실제 Tailscale 프록시의 헤더 처리, Mac 강제 종료 시 자원 정리는 이 검사로 증명하지 않았다. CLI 업데이트 시 같은 제한과 가상 파일 검증을 재확인해야 한다.
